# file_write Tool

`file_write` 是 LuckyAgent 的内置本地文件写入工具，用来创建或覆盖一个本地文件。它适合在任务需要生成真实文件、导出完整文档、写入配置模板、创建代码文件或保存产物时使用。

`file_write` 会把传入的 `content` 作为完整文件内容写入目标路径。如果目标文件已经存在，它会被覆盖。因此这个工具被标记为需要审批。

## 工具定义

实现位置：

- `internal/tool/builtin_fs.go`

注册信息：

```go
Name:       "file_write"
Category:   CatBuiltin
Source:     "builtin"
Permission: PermApprove
ShellAware: true
```

含义：

- `CatBuiltin`：这是核心内置工具，不依赖 skill 或 MCP。
- `PermApprove`：写入或覆盖文件会改变磁盘状态，默认需要审批。
- `ShellAware`：agent 可以向工具注入当前工作目录 `_cwd`，相对路径会基于该目录解析。

## 参数

`file_write` 接收两个参数：

| 参数 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `path` | 是 | 无 | 要创建或覆盖的目标文件路径。 |
| `content` | 是 | 无 | 完整文件内容。不是 diff，也不是追加内容。 |

示例参数：

```json
{
  "path": "docs/tools/example.md",
  "content": "# Example\n\nThis file was generated by file_write.\n"
}
```

## 执行流程

`file_write` 的执行过程是：

1. 读取必填参数 `path`。
2. 读取必填参数 `content`，没有提供时返回 `content is required`。
3. 通过 `resolvePathArg(args, "path")` 解析目标路径。
4. 如果路径解析失败，返回对应错误。
5. 使用 `os.MkdirAll(filepath.Dir(path), 0o755)` 自动创建父目录。
6. 使用 `os.WriteFile(path, []byte(content), 0o644)` 写入文件。
7. 返回写入字节数和目标路径。

成功输出类似：

```text
Written 42 bytes to /path/to/file.md
```

## 覆盖语义

`file_write` 是完整覆盖写入：

- 目标文件不存在：创建文件。
- 目标文件已存在：覆盖整个文件。
- 父目录不存在：自动创建父目录。
- 文件权限：写入文件权限为 `0644`。
- 父目录权限：自动创建的目录权限为 `0755`。

它不支持追加模式，也不支持局部替换。需要局部编辑时应使用 `file_patch`。

## 路径解析

`file_write` 和其他文件工具共用路径解析逻辑：

- 支持 `~` 和 `~/...` 展开到当前用户 home。
- 相对路径优先相对 `_cwd` 解析。
- `_cwd` 本身必须通过 sandbox 校验才会被采用。
- 路径清理后如果包含 `..`，会被拒绝。
- 最终路径必须通过 `validateSandbox`。

示例：

```json
{
  "path": "docs/tools/new-tool.md",
  "content": "# New Tool\n"
}
```

如果当前 `_cwd` 是仓库根目录，这会解析到仓库下的 `docs/tools/new-tool.md`，前提是 sandbox 允许该路径。

## 访问限制

`file_write` 使用 `validateSandbox` 做路径限制。当前允许范围包括：

- `~/.luckyagent/`
- 系统临时目录，例如 `/tmp/`
- `/dev/null`
- 测试场景下，如果 home 目录名是 `.lh-home`，也允许该 home 目录

明确拒绝的敏感路径包括：

- `~/.nanobot`
- `~/.ssh`
- `~/.gnupg`
- `~/.aws`
- `~/.config/gcloud`
- Windows gcloud 配置目录
- `/etc/shadow`
- `/etc/ssh`

此外，路径中包含 `..` 会被视为路径穿越并拒绝。

这些限制来自文件工具的路径解析层。由于 `file_write` 会改变磁盘状态，调用前还应结合用户意图和审批机制确认写入是明确需要的。

## 适合使用的场景

优先使用 `file_write` 的场景：

- 创建一个全新的 Markdown 文档。
- 导出完整报告、配置示例或生成产物。
- 写入新源码文件。
- 覆盖一个由 agent 完整生成、且用户明确要求重写的文件。
- 保存工具输出到一个确定路径。

示例：

```json
{
  "path": "docs/tools/file_write.md",
  "content": "# file_write Tool\n\n..."
}
```

## 不适合使用的场景

不优先使用 `file_write` 的场景：

- 修改已有文件中的几行：使用 `file_patch`。
- 追加内容到日志或列表：优先用更专门的工具或明确构造完整文件内容。
- 创建目录但不写文件：使用 `file_mkdir`。
- 移动或重命名文件：使用 `file_move`。
- 删除文件：使用 `file_delete`。
- 读取文件：使用 `file_read`。
- 生成图片或音频：使用 `image_generate` 或 `text_to_speech`，它们有自己的输出路径规则。

尤其不要为了小修改而先读全文件、手工拼接完整内容再用 `file_write` 覆盖。这样容易误删用户未注意到的内容。小范围编辑应使用 `file_patch`。

## 常见调用示例

创建 Markdown 文件：

```json
{
  "path": "docs/notes/example.md",
  "content": "# Example\n\nA short generated document.\n"
}
```

写入 JSON 配置示例：

```json
{
  "path": "examples/sample-config.json",
  "content": "{\n  \"enabled\": true,\n  \"name\": \"demo\"\n}\n"
}
```

写入临时文件：

```json
{
  "path": "/tmp/luckyagent-output.txt",
  "content": "temporary output\n"
}
```

## 和 file_patch 的关系

`file_write` 写完整文件。

`file_patch` 修改已有文件的一部分。

如果目标是“新增一篇完整文档”，用 `file_write` 合理。如果目标是“把某个函数里的参数改一下”，应使用 `file_patch`。

判断标准：

- 能完整、确定地生成整个文件：`file_write`。
- 只需要改局部，且要保留其他内容：`file_patch`。

## 和 terminal 的关系

不要优先用 `terminal` 手写：

```sh
cat > file <<'EOF'
...
EOF
```

也不要优先用：

```sh
echo "..." > file
```

正常文件写入应使用 `file_write`，因为它有统一的路径解析、权限标记、审计语义和清晰的返回结果。

`terminal` 只应在需要运行项目命令、构建脚本、测试工具或外部 CLI 时使用。

## 风险和注意事项

`file_write` 的最大风险是覆盖已有文件。

调用前应确认：

- 用户确实要求创建或覆盖文件。
- 目标路径正确。
- `content` 是完整文件内容。
- 不会覆盖用户未要求修改的文件。
- 对已有文件的小修改没有误用 `file_write`。

如果不确定目标文件是否存在，应先用 `file_read` 或 `file_list` 检查。

## 维护注意事项

如果后续修改 `file_write`，需要同步检查：

- 参数说明是否仍与 `FileWriteTool()` 一致。
- 是否仍使用完整覆盖语义。
- 是否仍自动创建父目录。
- 写入文件权限是否仍是 `0644`。
- 自动创建目录权限是否仍是 `0755`。
- 路径解析和 sandbox 规则是否变化。
- 是否增加了追加模式、覆盖保护或备份机制。
