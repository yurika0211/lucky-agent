# 多仓库协作与进度同步

## 1. 先确认归属

| 修改内容 | 提供方 | 常见消费方 / 需要同步的位置 |
| --- | --- | --- |
| Agent Loop、上下文、审批与会话执行策略 | 主仓 `agent/` | app 组装与 handler、根 launcher |
| 配置、模型协议、会话/记忆/RAG/MCP 后端 | runtime | Agent、app、根 manifest；配置示例与 Pages |
| 工具 schema、内置工具、Skills、工具适配 | tools | Agent、runtime、app、API/gateway 的适用调用方 |
| delegate/collab/autonomy/task 引擎 | orchestrator | tools/API、Agent 执行器与会话适配、app |
| HTTP/SSE/WS/gRPC 合同与通用恢复存储 | API | app handler、Android、其他协议客户端 |
| 平台协议与连接 | gateway | app/channelapp、运行配置与平台文档 |
| 插件包、安装、快照与信任状态 | plugins | Agent 插件运行时、app CLI/API、MCP 配置 |
| Android 页面、本地状态与协议消费 | Android | API/app 的相应合同与产品说明 |
| 构建、发布、产品配置与入口 | 主仓根模块 | 最终程序、部署流程、产品文档 |

这是职责表。是否使用某个新版实现，必须读取消费者 manifest 和实际选择的模块版本。
主仓根模块和 Agent 叶模块分开维护，依赖为 launcher → app → Agent → 组件；
runtime 和执行引擎不能反向导入 Agent/app。

## 2. 建立任务快照

开始时记录受影响仓库的 origin、默认分支、HEAD、当前分支、脏文件和 worktree。
目录改名不代表仓库身份改变。旧目录里保留的 `internal/*` 源码不代表当前主线。
worktree 移动后先检查 Git 登记；用 repair 修复已确认的路径，不自动删除旧工作区。

同一功能的进度至少包含以下状态，不把它们合并为一个“完成”：

| 功能 | 提供方提交 / PR | 默认分支 | 消费者选中版本 / PR | 文档 | 验证 | 运行状态 | 下一步 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 填功能名称 | 本地 / 已推送 / PR 链接 | 已合并 / 待合并 | 写实际版本与接入位置 | 已更新 / 待更新 | 命令、HEAD、结果或未运行 | 未发布 / 已构建 / 已部署 | 具体仓库与动作 |

核对开始和结束均写时间。多个任务同时提交时，以记录的提交快照说明结论；出现新合并
后刷新对应行。历史报告保留时间戳并指向当前总览，不让旧 PR 数量充当当前待办。

## 3. 开发与发布图分别核对

本地联合开发可以使用忽略的 `go.local.work`。其成功只能证明参与该工作区的源码能
协作，不能证明其他机器能下载发布依赖。

在消费者和最终 launcher 中读取公开依赖图：

```bash
GOWORK=off go list -mod=readonly -m all
```

需要验证实现时，按任务要求执行所属模块的检查；最终程序可检查：

```bash
GOWORK=off go build -mod=readonly -o lh ./cmd/la
```

Agent 有自己的 `go.mod`。根目录 `./...` 不遍历它，需要进入 `agent/` 分别检查。
仓库自带的可移植 `go.work` 则选择当前 root 与 Agent 源码，两种构建回答不同问题。

不要看到某个组件的最低版本较低，就判定产品漏接：Go 会在同一次构建选择一个版本。
核对最终选择的版本、目标能力是否包含、提交是否属于默认分支或合并内容等价。

## 4. 按依赖顺序交付

在用户授权的发布范围内：先处理提供方，再升级直接消费者，最后核对 launcher。
每个 PR 写清上游 PR、精确提交、测试/构建/CI 的实际状态和剩余依赖。
并行开发可以固定公开的上游 PR 提交；依赖 PR 合入后，核对该提交在默认历史中，或
证明最终合并的内容等价。不要在最终 manifest 留本机 replace。

PR head 改变或默认分支有并行变更时，保留其他工作并重新核对受影响检查。记录失败、
未运行、没有 CI、按条件跳过；只有实际成功的检查才能写通过。合并、发布产物和部署
分别记录。当前任务的授权不扩展到无关 PR。

## 5. 文档和笔记同时收尾

- 功能仓库：同步 `docs/` 与 README；合同、事件和配置变化同步具体消费者。
- 主仓：同步 `config.example.json`、产品说明和 GitHub Pages 源码。字段定义仍由
  runtime/config 维护，不在多个仓库复制 schema。
- Android：同步受影响的 HTTP/WS 字段及消费行为，不因为 Go 拆仓而导入 Go 源码。
- 项目笔记：维护一份当前跨仓库进度总览，按功能关联各仓 PR、选中版本与未完成项。
  本机 vault 位置放在工作区约定，仓库文档保持可移植。
- 对旧脏副本、分支与 stash：先做提交祖先、补丁或文件树比较，再判断是否遗漏；
  已交付的副本标成历史保留。未确认的差异保留为待核对，不自动恢复、清理或重复交付。
