# 长任务上下文与执行证据

长任务使用同一套输入预算：`context.max_context_tokens` 减去
`context_budget.reserved_ratio` 的回复预留。默认是 8000 × 75% = 6000
估算输入 token。普通对话、自动压缩、持久任务继续执行和验收都采用这一口径。
`limits.max_tokens` 仍是单次回答的输出上限。

旧 JSON 只有顶层 `max_tokens` 时会迁移为上下文上限；两个字段都显式存在时，
`context.max_context_tokens` 优先。旧 `lh config set max_tokens` 会同步两者；
新配置应使用 `lh config set context.max_context_tokens 16000`。
`config.example.json` 已包含所需字段，本次无需增加开关或更改存储格式。

## 规则、历史与实时结果

- 项目 `AGENTS.md` 从 SOUL/工具策略中独立出来，有单独的有界位置，避免长 SOUL
  在前面截断项目规则。超过项目预算时保留头尾，并标明省略。
- 历史读取与当前检索词无关，放在记忆/RAG 前面，使稳定前缀可复用。当前用户消息
  受到保护；持久任务另存原任务及验收条件，不靠摘要重新猜任务。
- 压缩记录仍完整保存在会话中。模型只看到有界的近期摘要投影，过多摘要会转换为
  归档索引和近期片段。摘要是历史证据，可以在最终裁剪时让位给新结果。
- 工具调用和全部匹配结果作为一个整体裁剪。相同优先级先选新组，再按原顺序返回。
  最近一轮工具调用/结果优先于旧检索证据。工具结果先去掉空行、重复行和进度行，
  再按路径、错误、命令等标识符优先保留，超长保护行才会收缩；结果仍给出全文读取引用。
- 自动压缩仍尊重开关；启用后，少数巨大消息造成实际输入超窗时，可越过最少消息数
  和冷却轮数限制。普通短会话仍使用原门槛。

完整排列、分类和软预算见[上下文编排策略](prompts/la-context-packing-strategy.md)。

### 探索结果交接

大批量检查结果可以交给探索子任务总结，但一批调用必须全部是已知的检查操作。
计量结果大小、决定是否交接和替换上下文中的原结果共用同一个调用分类规则。
合并后的 `data` 读取动作、`memory action=recall`、`document_read` 和兼容的旧读取
入口都参与计量；`memory action=remember/hygiene`、文件修改、RAG 索引、委派、
凭据工具及未知工具不交接。无约束的 `terminal` / `opencli` 命令也留在父上下文，
不能仅凭工具名称认定它们没有副作用。这样不会在一次混合读写后把写入结果替换掉。

## 读回省略的证据

模型工具 `context_history_read` 只读取宿主绑定的当前会话，不接受模型指定其他会话：

| action | 参数 | 返回 |
| --- | --- | --- |
| `list` | `offset`, `limit` | 压缩片段 ID、消息范围、总数、下一页 |
| `segment` | `segment_id`, `offset`, `limit` | 原保存摘要的分页内容 |
| `result` | `tool_call_id`, `offset`, `limit` | 原工具结果的分页内容，支持会话 blob |

文本 offset 以字符计数，每页最多 6000 字符，默认 4000；list 每页最多 50 个片段，
默认 20。`next_offset=-1` 表示读完。segment 读回保存的摘要，不会重新执行旧工具。
缺少宿主会话绑定、证据不存在或直接调用无上下文 handler 时返回错误。

## 执行状态与完成验收

持久任务每轮从已保存的 operations 和 pending 生成 `[Task State]`：成功/失败计数、
最近八项操作、待处理 ID 和下一动作。它是执行账本，不是自然语言“已完成”结论。
新工具调用前继续处理已记录的 pending，原有重放/恢复机制保持不变。

执行请求即使首轮只返回计划，也要走独立完成验收；普通问候和直接问答保留快速返回。
本地压缩把助手陈述标为未核实，显式的未来计划不能进入 `Completed work`。
验收同时保留最近 24 项操作和全部尚未解决的失败。预算不足时只移除较早的近期观察，
不会移除失败账本。相同工具、规范化参数和 shell 范围的后续成功会消解此前失败；
使用其他检查解决失败时，验收必须引用较新的真实成功操作 ID。无关失败必须明确解释
为何不影响原任务。每条 acceptance criterion 要有独立判定及候选答案或实际操作证据。
缺少判定、虚构 ID 或用失败操作充当成功证据会转为继续执行。语义相关性仍由模型判断，
不能保证消除所有错误完成判断。

## 验证与边界

回归覆盖长 SOUL 下的项目规则、少量巨大消息、连续十次压缩、归档/blob 读回与会话
隔离、末尾失败信息和完整工具轮次、仅返回计划后的继续执行，以及跨执行片的
100 次顺序工具操作和最终验收。已有取消、重启与重放测试也继续执行。

这些是确定性的模拟 provider/工具回归，没有进行真实模型的成功率、费用或延迟实验。
token 是估算值。最终同步/流式请求统一计入普通消息、结构化文本、工具调用参数和
实际发送的 schema。schema 先占预算，再按完整回合裁剪历史，并恢复原始图片、附件等
字段。可选 schema 按任务意图选择，目标为输入窗口的三分之一；显式点名、强制调用及
当前工具回合中的工具必须保留，可使用更多剩余预算。必需 schema 或当前输入无法放入时
在调用 provider 前明确报错，不静默删除当前请求。图片按 detail 使用固定余量，仍不是
供应商精确的视觉 token 计费。极长的当前任务或固定指令无法放入时会明确报预算错误。
项目规则超出专属位置时使用独立的头尾裁剪并标明省略；工具输出按行优先级裁剪，
首、中、尾都可能省略，需要主动读回证据。摘要本身也可能有错，不能代替工作区状态
和原工具结果。

重复检测的 last_results 旧正文会迁移为 SHA-256 摘要。原文仍在消息和操作证据中；
这是去除冗余副本，完整检查点仍会全量编码。持久化基准和发布图检查见
[Agent 核心加固](agent-hardening.md)。
